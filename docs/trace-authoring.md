# Trace 编写指南：断言密度

断言密度决定一条 trace 的语义强度，也直接决定 `heal_step` 自愈的成功上限——
**验证门判「步骤全绿」，不等于「意图达成」**。修错但流程恰好走通的 heal，
只有断言能拦。写 trace 就是给未来的自动修复立裁判标准。

## 意图步配方：每个改变状态的操作，后跟一个锁住结果的断言

| 操作类型 | 推荐断言 | 理由 |
|---------|---------|------|
| 认证/登录 | 登录态独有元素 `visible`（如「退出登录」） | 锁住认证成功，而不只是按钮点到了 |
| 打开弹窗/抽屉 | 标题 `visible`，且标题含业务标识 | 「教育事业群 — 干部明细」比「dialog 出现」强得多 |
| 关闭/删除 | 目标 `hidden` | 关闭动画期间元素仍在，立即断言会假过 |
| 导航 | `url-contains` 或目标页标志元素 `visible` | 路由错了元素也可能碰巧在 |
| 搜索/过滤 | **被滤除项 `hidden` + 保留项 `visible`** | 负向断言是过滤意图的最强锁（见下） |
| 创建/提交 | 成功提示 `visible`，或 `extract` 记录 ID 后再查 | 把运行时值串成完整业务链 |

## 案例：smoke-login 的搜索断言（2026-09-22 审计实测）

搜索「教育事业群」后，选什么断言经历了三次实测迭代，教训值得记住：

1. **正向断言「结果卡片 visible」不可用**——该 SUT 的部门页有卡片/树两种视图，
   搜索结果形态随视图模式变，同一条 trace 在不同视图下回放结果不同。
2. **负向断言「被滤除项 hidden」可靠且更强**——搜索后「安徽讯学教育科技有限公司(体系外)」
   必然消失；搜索前它必然在。断言在「不做搜索必失败」的意义上锁死了过滤意图，
   且与视图模式无关。已固化进 traces/smoke-login.json 第 12 步。
3. **异步结果 = wait + assert 组合**——过滤/展开如果晚于动作返回，
   先用显式 `wait`（visible/hidden）等到条件，再 `assert` 记账。
   断言管语义，wait 管时序，两者都留在 run-record 里。

## 反模式

- **每步都断**：拖慢 replay，前置准备步（fill 输入框）无断言价值。
- **断动态文案**：含计数/时间戳的文案（「共57人」）会随数据漂移误报；
  选结构稳定的标识（名称、标题、路由）。
- **依赖易变布局的元素形态**：卡片视图/树视图这类用户可切换的呈现层，
  断言要选视图无关的锚（被滤除项、URL、业务标识）。
- **与下一步重复的断言**：下一步 fill 已隐含存在性，不必再断一次。

## 自愈视角的补充

- heal 写回前会全量重放，**断言越密，验证门越能拦住「修错但走通」的修复**；
- 断言失败的步骤 `heal_step` 会拒修（可能是产品真 bug）——断言同时也是
  人工介入的触发器，写的时候把它当成给同事看的验收标准来写。
